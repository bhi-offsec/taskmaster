## [Unreleased]

### Added
- **Finding Templates — a reusable vulnerability library** (the pwndoc "vulnerability template" concept, native to Taskmaster). New `finding_templates` table + CRUD in `state/reporting.py` (`create/get/list/update/delete_finding_template`), storing only the engagement-agnostic content of a finding (title, severity, category, description, impact, generic proof-of-concept, remediation, references, CVSS). New **Finding Templates** dashboard tab (replaces the flat Report Findings list) with severity/category/text filters. Two flows tie it to real findings: **Use** instantiates a template into a new finding under an engagement (`template_to_finding_payload` → `create_finding`, copying references), and **Save as template** on a finding's edit page promotes it back into the library (`finding_to_template_payload`). **Why:** every engagement re-authored the same boilerplate write-ups by hand. **UX impact:** start a finding from a vetted template and only fill in the instance detail (affected target, evidence); good findings compound into the library over time.
- **One-time pwndoc import** (`scripts/import_pwndoc_templates.py`). Seeds the native library from a pwndoc-ng `list_vulnerabilities` JSON export: maps `description`→description, `observation`→impact, `remediation`→remediation, `cvssv3`→cvss_vector, `references[]`→references (http(s) only), `category` passes through (it already mirrors the Taskmaster enum), severity defaults to Info. Includes a compact HTML→Markdown converter (paragraphs, headings, bold/italic/code, links, ordered/unordered lists, and tables as Markdown pipe tables) since pwndoc stores rich HTML; strips the `BHI-OFFSEC-…` title prefix and de-duplicates by title. It is a content copy, not a live sync — no pwndoc IDs are stored and re-running is idempotent, keeping the existing "no pwndoc coupling" rule intact.
- **Copilot intelligence — `suggest_next_action`.** A read-only planning tool that inspects the whole state (per-engagement or global) and returns the prioritized gaps in one call: failed executions, executions missing an `interpretation`, work that's queued-but-unprovisioned, untriaged observations, report findings that aren't yet render-ready, phase-coverage holes, and threat-model status. **Why:** the orchestrating LLM previously had to reconstruct "what should I do next" by hand from scattered tool calls at the start of every session and after every stall. **UX impact:** one call orients the operator; the guidance surfaces this as the thing to call at session start or any time you're unsure what's next.
- **Playbooks — `request_playbook`.** Expands a named playbook (call it bare to list them; registry in `policies/playbooks.py`, e.g. `web-recon`, `subdomain-recon`) or an inline `steps` list into a dependency chain against a single target: each step runs only after the previous one COMPLETES, and the chain is cancelled if any step fails. **Why:** multi-step recon/enum sequences previously had to be hand-sequenced — queue, wait, read, queue the next — which is tedious and error-prone. **UX impact:** one call lays down an ordered, self-gating sequence instead of babysitting each step.
- **Task dependencies (`depends_on`).** `request_security_action` accepts `depends_on` (a list of prerequisite execution ids); a queued execution stays out of the ready set until all prerequisites are COMPLETED, and failure/cancellation of a prerequisite recursively cancels everything blocked on it (new terminal `CANCELLED` state). New `depends_on TEXT` column (online-migrated), `dependencies_satisfied()` / `cancel_blocked_dependents()` in `state/state.py`, and a readiness gate on the QUEUED→CLAIMED transition. **Why:** the queue had no notion of ordering, so dependent work could be claimed before its prerequisite finished. **UX impact:** the dashboard shows a `⛓ N` chip on dependent rows and a cancel reason on cascade-cancelled ones, so a skipped step reads as an intentional cascade rather than a mysterious failure.
- **Canonical operational guide + cross-client delivery.** A single distilled `OPERATIONAL_GUIDE.md` is now the source of truth for *how to drive Taskmaster*, delivered to the orchestrating LLM three ways so it lands regardless of client or working directory: (1) its "Core loop" section is served through the MCP `initialize` handshake (`instructions`), (2) the whole file is served by a new `get_operational_guide` MCP tool, and (3) filesystem `@import` pointers in the user's global Claude/Codex config back it up. The `request_security_action` / `request_playbook` descriptions carry a "new to this session? call `get_operational_guide` first" nudge. **Why:** the detailed workflow previously lived only in repo-local `CLAUDE.md`/`AGENTS.md`/`GEMINI.md`, invisible when orchestrating from another directory or a non-Claude client (Codex, Antigravity). **UX impact:** consistent methodology across Claude Code, Codex, and other MCP clients without per-project setup.
- **Engagement Overview landing page** (`/overview`, now the default route). The screen-share home: a findings-by-severity bar chart (reusing the accessible severity ramp, with direct count labels so identity is never color-alone), phase-coverage meters (completed/total per phase), and Recent activity + Latest findings lists — all honoring the engagement scope selector. New `api.get_overview()`. **Why:** the dashboard opened onto a dense executions table with no at-a-glance state. **UX impact:** a clean, presentable summary to open a review on.
- **Grouped, icon-based navigation.** The sidebar is split into **Operations** (Overview, Executions, Targets, Agents, Observations) and **Reporting** (Engagements, Report Findings) with an inline-SVG icon set replacing the old HTML-entity glyphs, active item highlighted. **Why:** a flat, unlabeled nav gave no sense of the two distinct workflows. **UX impact:** the ops-vs-reporting split is legible at a glance.
- **Health endpoint + graceful shutdown.** Both listeners answer `GET /healthz` with `{"status":"ok"}`, and the server installs SIGTERM/SIGINT handlers that shut both HTTP servers down cleanly. **Why:** there was no liveness probe and no clean stop (resolves the "no graceful shutdown handling" known issue). **UX impact:** the server can be health-checked and stopped without orphaning threads.
- **Orphan sweep in the agent reaper.** The reaper now force-fails executions stuck in CLAIMED/RUNNING whose executor container no longer exists (past a grace period, default 300s via `orphan_timeout`), releasing the target lock and cascade-cancelling dependents. `reap_once` reports `{reaped, orphans_recovered}`. **Why:** a container that vanished mid-action (crash, manual `docker rm`) left its row wedged and its target locked until manual recovery. **UX impact:** the fleet self-heals from lost workers instead of silently blocking a target.
- **Fixed finding categories (mirrored from pwndoc-ng).** Finding `category` was previously a free-form string the LLM could invent, with only a cosmetic hardcoded dashboard dropdown. It is now a fixed set — the 18 categories from the pwndoc-ng `vulnerabilitycategories` collection (`Web`, `OS-Windows`, `Multi`, `Cloud-AWS`, `API`, `Containers`, `Infrastructure`, `OS-Multi`, `Cloud-GCP`, `Software`, `Thick-Client`, `ActiveDirectory`, `OS-Linux`, `Mobile-Android`, `CI-CD`, `Cloud-Azure`, `Okta`, `AI-LLM`) plus two Taskmaster buckets: `TBD` (default when omitted) and `Other` (catch-all). Exposed as an `enum` on the `create_reporting_finding` / `update_reporting_finding` MCP schemas and driving the dashboard dropdown. `normalize_category()` coerces rather than rejects: an omitted/blank value becomes `TBD`, an off-list value becomes `Other`, and the stored value is returned so the coercion is visible. Defined as `FINDING_CATEGORY_ORDER` in `state/reporting.py`; keep it in sync when pwndoc categories change.
- **Threat model component (evidence-grounded)**: a per-engagement threat model driven by the orchestrating LLM, modeled after a full evidence-grounded methodology rather than a flat STRIDE table. Backed by `threat_models` plus twelve entity tables (`tm_assumptions`, `tm_roles`, `tm_assets`, `tm_terminal_goals`, `tm_attack_surface`, `tm_trust_boundaries`, `tm_attack_paths`, `tm_test_objectives`, `tm_existing_mitigations`, `tm_recommended_mitigations`, `tm_open_questions`, `tm_evidence_notes`). Cross-references between entities are human-readable ref strings the LLM authors (e.g. an attack path's `impacted_assets` = "CA-1, CA-4"). Every element is evidence-tagged (`EVIDENCED` / `USER-CONFIRMED` / `ASSUMED` / `OUT-OF-SCOPE`), and `EVIDENCED` links to a Taskmaster `execution_id`/`finding_id`. Supports the two-pass workflow (first-pass model → validation interview → refinement that propagates answers), with a `draft → in_review → final` status and assumption/open-question tracking. MCP tools: `assemble_threat_model_context`, `create_threat_model`, `list_threat_models`, `get_threat_model`, `update_threat_model`, a generic `add_threat_model_entry` / `update_threat_model_entry` / `delete_threat_model_entry` (dispatch on `entity_type`), and `export_threat_model_markdown`. The engagement workspace renders the model as native, auto-escaped HTML tables (summary tables + detailed attack paths); the full deliverable exports as reference-format `<name>-threat-model.md` (MCP tool or a dashboard download at `/reporting/threat-models/<id>/export`).
- **Session material mount for agents**: a dedicated read-only channel for user-supplied secrets (cookie exports, auth tokens, Playwright `storage_state`) so they never travel through the spawn payload, execution request, or audit log. Drop files in a directory and `spawn_agent` bind-mounts it read-only at `/session` on every agent and exports `SESSION_DIR=/session`. `BaseBrowserSkill` auto-loads `/session/storage_state.json` (filename overridable via `STORAGE_STATE_FILE`) into every browser context, so Playwright/patchright/camoufox skills start authenticated with no extra arguments. Replaces the ad-hoc "spin up a local HTTP server to transfer the file into the container" workaround. The directory defaults to `<WORK_DIR>/runtime/session/` (override with `TASKMASTER_SESSION_DIR`); for a shared server whose `WORK_DIR` differs from the caller's project folder, pass `session_dir` (an absolute host path, validated to exist) on `spawn_agent` to point at a folder inside the engagement directory.
- **Executions are bound to a reporting engagement.** New nullable `engagement_id` column on the `executions` table (online-migrated onto existing databases, with an `idx_executions_engagement` index). `request_security_action` accepts an optional `engagement_id` (validated — an unknown id is rejected) and tags the queued execution with it; `request_reporting_docx` tags render executions with the explicit engagement or the one shared by its findings. This replaces the earlier scope-asset/finding-source *derivation*, which could not tell apart two engagements assessed over the same or overlapping scope.
- **Global engagement scope selector**: a dashboard-wide selector (top of the main pane, persisted in the `tm_scope` cookie) that filters the stats bar plus the Executions and Observations lists to a single engagement by its `engagement_id`. Selecting "All engagements" restores the global view; a stale cookie (deleted engagement) is validated server-side and ignored so it can't pin every metric to zero. Untagged/legacy executions appear only under "All engagements".
- **Assign an execution to an engagement from the dashboard**: the execution detail panel gained an engagement dropdown (`POST /executions/<id>/engagement`) to tag or re-assign an execution after the fact — useful for legacy executions queued before the engagement existed, or to correct a mistag.
- **Engagement workspace dashboard UI**: new **Engagements** nav item and two pages that make the reporting database engagement-centric rather than execution-centric.
  - `/reporting/engagements` — engagement overview cards (client, status, finding/open counts, scope count, per-severity chips) plus an inline create form.
  - `/reporting/engagements/<id>` — the engagement hub: severity distribution and status-pipeline rollups, a filtered findings list with an **inline status control** (change `draft → needs_review → confirmed → reported → …` per finding via htmx without leaving the page), a **scope panel** that reads and edits `report_assets` (add/remove hosts, domains, URLs — previously unreachable from the UI), and a **render history** panel listing rendered deliverables with one-click "Queue DOCX".
  - New `api.py` helpers: `get_engagements_overview`, `get_engagement_workspace`, `get_engagement_findings`, `get_engagement_renders`, plus severity/status count helpers. New `state/reporting.py` helper `delete_asset`.
- **Rendered DOCX download** from the dashboard: `GET /reporting/download?exec=<id>&i=<index>` streams a report execution's artifact as an attachment. Downloads are addressed by execution + artifact index (no raw path input); `api.resolve_artifact_host_path` maps container paths (`/reports/…`, `/loot/…`) to host files under `runtime/reports` / `runtime/loot` and rejects — via a `realpath` containment check — anything that resolves outside those roots or does not exist. Render-history artifacts are now download links.
- **Findings rollup in the stats bar**: a second stats row shows total / open / reported report findings plus per-severity counts, alongside the existing execution counters.
- **Report findings dashboard UI**: `/reporting/findings` page for the database-backed reporting workflow. It lists curated report findings separately from execution observations, supports engagement/status/severity/search filters, creates engagements, creates and edits report findings, appends evidence and references, and queues DOCX renders through the existing `request_reporting_docx` path.
- **Three-tier bot-evasion ladder** for fingerprint-protected targets (Akamai, Cloudflare, Datadome, etc.) where vanilla headless Chromium and Burp's outbound TLS both get blocked at the transport layer (`ERR_HTTP2_PROTOCOL_ERROR`, silent 403, challenge page, or "Burp Suite" upstream-failure page):
  - **`curl_cffi`** + **`httpx[http2]`** installed in the Kali image (`executors/Dockerfile`). `python` and `skill` actions can now `from curl_cffi import requests; requests.get(url, impersonate="chrome124")` for JS-free recon (API probes, OAuth/redirect chasing, sitemap/robots, raw endpoint enum) with a real Chrome/Firefox/Safari TLS+HTTP2 fingerprint.
  - **Patchright** browser engine in the Playwright image — anti-detection Playwright drop-in on patched Chromium. **Default** for `agent_type: "playwright"` going forward.
  - **Camoufox** browser engine in the Playwright image — fingerprint-hardened custom Firefox. Escalation tier for the cases Patchright still gets flagged.
  - **`browser_engine` argument on `spawn_agent`** (`"playwright" | "patchright" | "camoufox"`, default `"patchright"`). Propagated into the container as `BROWSER_ENGINE` and consumed by `BaseBrowserSkill` and raw `playwright` scripts.
  - **`BaseBrowserSkill` engine dispatch** (`skills/browser.py`): `run()` now branches on the resolved engine (kwargs → `BROWSER_ENGINE` env → class attr). Camoufox's combined browser+context launcher is wrapped behind the same `page, context` contract, so existing skills work unchanged across all three engines. JSON envelope gains an `engine` field; `tool_version` is sourced from whichever engine actually ran.
  - Selection guidance added to `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, the `request_security_action` tool description, and the MCP schema for `spawn_agent.browser_engine`. Decision rule: pick the lowest tier that gets the data; escalate on `ERR_HTTP2_PROTOCOL_ERROR` / silent 403 / visible challenge.
  - New tests in `tests/unit/test_browser_skill.py` exercise per-engine version resolution. `_playwright_version()` renamed to `_engine_version(engine)`.
- **Reporting executor** (`executors/Dockerfile.reporting` + `executors/report_operator.py`): dedicated `report-operator` container (slim `python:3.12` + `docxtpl` / `python-docx` / `jinja2` / `pyyaml`) that exclusively claims tasks with `action_type: "report_skill"`. Mirrors the playwright operator's lifecycle: claim → start → run skill → complete, with a server-error log on every state-write rejection.
- **`skills/reporting.py`**: `BaseReportSkill` ABC — non-CLI counterpart to `BaseSkill` / `BaseBrowserSkill`. Subclasses implement `render(**kwargs) -> dict`; the orchestrator handles timing, artifact tracking, and JSON envelope assembly.
- **`skills/reporting.FindingDocxReport`**: first reporting skill. Takes a `finding` dict, a list of `findings`, or a `findings_path` (YAML/JSON) and renders one branded docx per finding via docxtpl. Writes to `/loot/reports/` by default; supports `template_path` and `output_dir` overrides. Jinja autoescape is enabled so payloads containing `<`, `>`, `&` (typical XSS PoCs) render correctly instead of corrupting the document.
- **`templates/finding_template.docx`**: docxtpl-tagged finding template — produced from a hand-formatted source docx by `scripts/build_finding_template.py`. Layout (fonts, table widths, headers/footers) is preserved from the source; only placeholder text is rewritten with Jinja tags.
- **`scripts/build_finding_template.py`**: one-shot builder that converts an example docx into the docxtpl template. Re-runnable when the source layout changes; fails loudly on layout drift via a snippet-based sanity check.
- **`templates/README.md`**: guide for producing a docxtpl template from a provided example docx — covers the layout contract, the builder script's mental model, the autoescape gotcha, and how to adapt the builder for a new template variant.
- **Finding-content style contract** for the reporting pathway. Documented in the `skills/reporting.py` module docstring, `templates/README.md`, and the agent guides (`AGENTS.md`, `GEMINI.md`, `CLAUDE.md`). Core rules: plain, succinct, client-facing language; each field has one job (description = what / impact = why it matters / PoC = how to reproduce / remediation = specific actions); **no references to `Findings.md`, `recon-data.md`, `F-NNN` triage IDs, or `§N.M` recon section markers** — those internal working files are not shared with the client, and citing them in the deliverable creates confusion.
- **New `action_type: "report_skill"`** in `request_security_action` — invokes a `BaseReportSkill` subclass by name (e.g. `reporting.FindingDocxReport`), mirroring the `playwright_skill` pathway. Requires the `skill` field.
- **New `agent_type: "reporting"`** in `spawn_agent` — selects the `report-operator` image and `reporting-agent-*` container name.
- **`make build-reporting`** target and inclusion in `make build`.
- Reporting deliverables are recognized by `cleanup_agents` (new `reporting-agent` prefix + `report-operator` image name).
- **Agent reaper** (`tools/reaper.py`): background daemon thread started by the MCP server that periodically stops Taskmaster-managed agent containers under three conditions — hard age cap (default 4h), stale heartbeat on a claimed/running execution (default 2h since `updated_at`, also force-fails the execution to release the target lock), and idle past grace (default 15 min with no claimed work). Configurable via `TASKMASTER_REAPER_ENABLED`, `_INTERVAL`, `_IDLE_TIMEOUT`, `_STALE_TIMEOUT`, `_MAX_AGE`.
- 9 new unit tests in `tests/unit/test_reaper.py` covering each reap path, the keep cases, non-Taskmaster container filtering, and docker-timestamp parsing.
- **Burp Suite CA trust** in both agent images: drop a DER-exported Burp CA at `executors/burp-cacert.der` (gitignored, per-developer) and it's installed into the system trust store via `update-ca-certificates`. Kali tools and Chromium will then accept Burp's MITM cert without `verify=False` workarounds. Uses a BuildKit wildcard COPY so builds still work when the cert is absent.
- **`heartbeat_execution` MCP tool + automatic worker heartbeat.** New tool (`state/state.py::heartbeat_execution`, `tools/heartbeat_execution.py`) refreshes a RUNNING execution's `updated_at` without changing status or touching target locking. `executors/kali_operator.py` and `executors/mobile_operator.py` now run each skill invocation under a background thread that calls it every `TASKMASTER_HEARTBEAT_INTERVAL` seconds (default 300). **Why:** both operators block synchronously for the full duration of a skill's subprocess — a nuclei scan can run tens of minutes to hours — so `updated_at` previously froze the instant RUNNING started, making a legitimately long scan indistinguishable from a genuinely hung one to the reaper's 2h stale-heartbeat check.
- **`resplit_timed_out_shard` MCP tool** (`tools/resplit_timed_out_shard.py`). Narrows and requeues a shard whose `findings.timed_out` came back `true`: splits a comma-separated `tags` argument into `split_factor` groups and requeues via `request_batch` for `web.NucleiScan`, or escalates `first_party`/`first_party_depth` for `mobile.MobileNucleiScan`; returns `splittable: false` with a reason for anything else rather than guessing. **Why:** nuclei is hard-killed (SIGKILL) on a wall-clock timeout, so there's no per-template resume checkpoint to pick up from — narrowing scope and retrying is the real fix, and leaving it as prose in `OPERATIONAL_GUIDE.md` meant every orchestrating LLM had to re-derive and remember to apply it; a tool call is deterministic and cheaper.
- **`rate_limit` argument on `web.NucleiScan`.** Passes through to nuclei's `-rate-limit` — the only backpressure lever against a slow/throttling target (nuclei has no backoff of its own), previously unexposed on the skill.

### Changed
- **Removed the flat cross-engagement "Report Findings" list page/tab.** Each engagement workspace already lists its own findings, so a global findings list was redundant; the nav slot now hosts **Finding Templates**. The finding create/edit form and all per-finding routes (`/reporting/findings/new`, `/…/edit`, status/evidence/references POSTs) are unchanged — they back the engagement workspace's "New Finding" flow. The bare `/reporting/findings` path now redirects to `/reporting/engagements`.
- **Dashboard moved to its own loopback listener + a table-driven router.** The server now runs two HTTP listeners: the MCP JSON-RPC endpoint on `TASKMASTER_HOST:TASKMASTER_PORT` (default `0.0.0.0:5000`, reachable by agent containers) and the dashboard on `TASKMASTER_DASHBOARD_HOST:TASKMASTER_DASHBOARD_PORT` (default `127.0.0.1:5001`, loopback-only). The dashboard's request handling was extracted into `dashboard/webapp.py` behind an explicit regex route table (`Router`), replacing the former ~360-line `if path == …` chain. **Why:** the MCP endpoint must bind an interface agent containers can reach, but the dashboard should not be exposed beyond the machine — a single 0.0.0.0 listener couldn't satisfy both, and the monolithic dispatcher made routing changes fragile. **UX impact:** the dashboard is private by default while agents still connect, and adding/reordering a route is a one-line change.
- **Executions table decluttered.** Removed the ID column (the full id is still shown when a row is expanded); long target strings are truncated with an ellipsis + hover tooltip; timestamps stay on one line; and the table scrolls rather than clipping. **Why:** verbose targets were pushing the trailing **Updated** column out of view, and the ID column duplicated information available on expand. **UX impact:** every column — including Updated — is readable at the default width.
- **Stats bar shown only on the Overview page.** The execution/finding counter bar previously rendered on every page; it now appears only on Overview. **Why:** with the Overview page carrying the counters plus richer charts, repeating the bar on Executions/Targets/Agents/Observations was redundant noise. **UX impact:** the working pages lead with their own content instead of a repeated header.
- **Targets and Agents lists now honor the engagement scope selector**, and the selector is hidden on the Engagements and Report Findings pages. **Why:** only the stats bar, Executions, and Observations respected the scope before, so Targets/Agents showed cross-engagement data even with an engagement selected; meanwhile the Engagements/Report Findings pages carry their own engagement filters, making the global selector redundant there. **UX impact:** selecting an engagement now scopes every operations view consistently, and the reporting pages aren't cluttered with a control that doesn't apply.
- **`CANCELLED` is a first-class dashboard status** — status badge, stats-bar card, and an executions filter option — reflecting the new dependency-cascade terminal state.
- **Report finding bodies now render markdown in the dashboard.** The engagement workspace passes `description`, `impact`, `proof_of_concept`, and `remediation` through the same lightweight markdown filter used for execution analysis (headers, lists, inline/fenced code), so stored finding content reads like the DOCX output instead of flat text. A finding's `source_execution_id` is now a deep-link to the originating execution.
- **Dashboard naming split**: the old execution-derived **Findings** view is now **Observations** (`/observations`, `/api/observations`) to avoid conflating raw worker output with client-facing report findings. `/findings` and `/api/findings` remain compatibility redirects/aliases.
- **Runtime layout reorganized under a single `runtime/` umbrella.** Loot, reports, audit logs, and state DB now live at `<WORK_DIR>/runtime/{loot,reports,audit,state}/` instead of being scattered across `audit/loot/`, `audit/`, and `state/` at the top of `WORK_DIR`. One folder to gitignore, one to delete, no more namespace collision between the on-disk `state/` and the `state/` Python package, and no `taskmaster/taskmaster/` visual collision when running in-place from the project root. `config.py` now exposes `RUNTIME_DIR`, `LOOT_DIR`, `REPORTS_DIR`, `AUDIT_DIR`, and `STATE_DIR`; downstream callers (`state/storage.py`, `audit/audit_manager.py`, `tools/spawn_agent.py`, `Makefile`, `scripts/cleanup.sh`, `.gitignore`) updated. Per-engagement isolation continues to work through `TASKMASTER_WORK_DIR`. No auto-migration — move any existing `audit/`/`state/` into `runtime/` once by hand.
- **`FindingDocxReport` now emits a single combined docx for any number of findings.** The template body is wrapped in `{%p for finding in findings %}…{%p endfor %}` with a hard page break between findings, so one `doc.render()` call produces one output file. Filename derives from the common dotted prefix of the finding ids (e.g. `BHI-OFFSEC-25.05-findings-2026-06-10.docx`) or the target slug when ids don't share one. Single-finding callers (`finding=…`) keep the per-finding `{id}-{title}.docx` naming. Output defaults to `/reports/` (host `runtime/reports/`) via a new bind mount, falling back to `/loot/reports/` when the mount is absent. The envelope's `findings` now returns `{output_path, finding_ids, template_path}` instead of a `rendered: [...]` list. Builder script (`scripts/build_finding_template.py`) updated to emit the wrap on re-runs.
- `make build` now builds **all three** agent containers (Kali + Playwright + Reporting). Use `make build-kali`, `make build-playwright`, or `make build-reporting` for partial rebuilds.
- `kali_operator.py` skip-list extended: `report_skill` joins `playwright`/`playwright_skill` as action types the Kali operator leaves in the queue for its dedicated executor.
- Direct project dependencies now include `docxtpl`, `python-docx`, and `pyyaml` so the reporting renderer runs on the host (e.g. for local smoke tests, dashboard-side rendering experiments) without spinning up the container.
- Planner-facing execution guidance now makes provisioning explicit: `request_security_action` only queues work, `spawn_agent` is the default next step unless a compatible live worker has already been verified for the target, and `query_execution_status` is positioned as a debugging/recovery tool rather than the standard monitor path.
- Added the same provisioning guidance to `CLAUDE.md` and a new repo-local `AGENTS.md` so non-Gemini agents receive the same workflow expectations.
- `spawn_agent` proxy is now **opt-in per call**: pass `proxy_url=...` explicitly to route container traffic through an intercepting proxy. The previous fallback to `.env`/shell `HTTP_PROXY` is removed — Docker containers reach external networks directly, and the always-on proxy injection was a leftover from the macOS-VM era that broke whenever Burp wasn't listening. Setting `HTTP_PROXY` in `.env` no longer affects spawned agents (`.env.example` updated to reflect this).
- `configure_proxychains` (kali operator) now parses `$HTTP_PROXY` to learn the upstream host/port instead of using `$TASKMASTER_HOST` and a hardcoded `8888`. Tools invoked via `proxychains4` now flow through the same upstream as `HTTP_PROXY`-aware clients (curl, requests, etc.); skips configuration silently when no proxy is set.
- `query_execution_status` now returns a slim projection by default (status, phase, target, executor, `updated_at`, `seconds_since_update`, `has_result`, `has_interpretation`) instead of dumping the full execution record — avoids kilobytes of request-payload and result-body bloat on every poll. Pass `verbose: true` to get the original full-record shape for debugging. `seconds_since_update` lets the orchestrator detect a likely-stuck worker without waiting for the server-side reaper.
- `spawn_agent` now bind-mounts the host `templates/` directory onto `/app/templates` for reporting agents, so template edits take effect on the next spawn without rebuilding `report-operator`. The `COPY templates /app/templates` step in `Dockerfile.reporting` is retained as a fallback when the host directory is missing (e.g. CI / shipped images). `templates/README.md` updated to reflect the new dev flow.

### Fixed
- **Targets "Show Details" did nothing for URL or space-containing targets.** The detail route packed the target into a path segment matched with `[^/]+`, so any target containing a slash (every `https://…` target) failed the match and 404'd; targets with spaces failed to resolve. The target now rides as a URL-encoded query param (`/api/targets/detail?target=…`), which round-trips slashes and spaces. Agents were unaffected because `executor_id` is always a clean container name.
- **Targets and Agents detail panels couldn't be collapsed once opened.** The "Show Details" button only hid itself (`display:none`), with no way to bring the detail back down. Both are now real show/hide toggles (`window.toggleDetail`): the slot lazy-loads once via htmx, and each click flips visibility while the label swaps between **Show Details** / **Hide Details**. Poll-pause was retargeted to `.detail-slot:not(.collapsed)` so a 5-second refresh can't wipe an open panel, and polling resumes once it's collapsed.
- **Reporting executor was invisible to MCP clients.** `spawn_agent`'s `agent_type` enum in `server.py` was hardcoded to `["kali", "playwright"]`, even though the handler and `request_security_action` (with `action_type: "report_skill"`) already supported reporting. LLMs reading the MCP schema concluded no reporting executor existed and fell back to running `FindingDocxReport` in a Kali python sandbox, where the host-mounted template path doesn't exist — so they hand-rolled minimal `python-docx` templates and produced unbranded deliverables. Enum and description now expose all three executor types. Stale guidance in `GEMINI.md` and the `cleanup_agents` docstring updated to match.
- **Wedged target locks**: both operators previously discarded the responses from `start_execution`, `complete_execution`, and `fail_execution`. If one execution got stuck `RUNNING` (e.g. an agent crash mid-action), every later CLAIMED→RUNNING transition for that target was silently rejected by the target-lock policy, the operator kept running the action and failing every state write, and rows stayed at CLAIMED until the reaper swept them — with no diagnostic signal anywhere. Operators now check each response: a rejected start skips execution with a logged reason, and rejected complete/fail calls print the server's error so the wedge is visible in `docker logs`.
- **Reaper discarded partial scan output it force-killed.** `_fail_execution_for_reap` (`tools/reaper.py`) overwrote a reaped execution's `result` with a generic failure string even though nuclei's `-jsonl` output survives the `docker rm` on the shared `/loot` bind mount. It now globs `/loot` for a matching partial artifact (heuristic: skill name + target substring + mtime not older than the execution's `created_at`) and appends the path(s) into the failure reason instead of leaving the surviving data orphaned.
- **`mobile.MobileNucleiScan` silently ignored a `scope` argument instead of erroring or using it.** The skill's own `package` override kwarg is named `package`, but the result's scope-note field is named `scope` — a naming collision that led an orchestrating LLM to pass `scope=<package>`, which `analyze(**kwargs)` silently absorbed and dropped, falling through to the manifest-derived package instead. `_resolve_targets` (`skills/mobile.py`) now accepts `scope` as an alias for `package`.
- **`BaseSkill`'s default timeout handling silently discarded partial results.** `execute_shell`'s `TimeoutExpired` path (`skills/base.py`) returned only an error string — no `timed_out` flag, no buffered stdout/stderr — and `run()` short-circuited before `parse_output` ever ran. Any skill relying on the base default (as opposed to the hand-rolled overrides already in `web.NucleiScan`/`mobile.MobileNucleiScan`) lost everything on a timeout even when the underlying tool had already written real output to `/loot`. `execute_shell` now returns `timed_out: True` plus whatever stdout/stderr had buffered, and `run()` still calls `parse_output` in that case (status becomes `partial`), matching the pattern the two nuclei skills already used; the JSON envelope also gains a top-level `timed_out` field.
